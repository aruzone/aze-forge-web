# Corporate TLS validation

A TLS client verifies the requested service identity against the certificate it received, checks the certificate's validity interval, and validates a certification path to a trust anchor. Treat those as separate observations. <https://www.rfc-editor.org/rfc/rfc9525.html#section-6> <https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5> <https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.1>

## Diagnostic to owner

| Client diagnostic or observation | What to inspect | Operational owner |
| --- | --- | --- |
| Hostname mismatch | Compare the requested host with the presented leaf certificate's `dNSName` entries. TLS service-identity matching uses `dNSName` in `subjectAltName`; a DNS wildcard can match only as the complete left-most label. <https://www.rfc-editor.org/rfc/rfc9525.html#section-6.3> | If the failing client received the public-origin certificate, the server certificate and deployment owner owns the repair. If it received a leaf signed by the enterprise inspection CA, the corporate TLS-inspection owner owns the re-signed leaf and policy. An inspection service creates a separate client connection and presents a certificate signed by the enterprise CA. <https://learn.microsoft.com/en-us/entra/global-secure-access/tutorial-internet-access-tls-inspection#how-does-tls-inspection-work> |
| `certificate has expired` or `certificate is not yet valid` | Check the presented certificate's `notBefore` and `notAfter` against the client's current time. X.509 defines certificate validity as that interval, and path validation takes the current time as an input. <https://www.rfc-editor.org/rfc/rfc5280.html#section-4.1.2.5> <https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.1> | The owner is the signer of the certificate the client received: server deployment for the public-origin certificate, corporate TLS inspection for an enterprise-signed replacement, or endpoint management when the client clock is wrong. The inspection owner must deploy and rotate its root before inspection is enabled. <https://learn.microsoft.com/en-us/entra/global-secure-access/how-to-transport-layer-security-settings-managed-certificate#download-and-deploy-the-root-ca-certificate> <https://learn.microsoft.com/en-us/entra/global-secure-access/how-to-transport-layer-security-settings-managed-certificate#rotate-a-microsoft-managed-certificate> |
| `unable to get local issuer certificate`, `unknown CA`, or an untrusted chain | Record the leaf, each intermediate, and the trust anchor the client attempted to use. PKIX path validation takes a trust anchor and a prospective certification path as inputs. <https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.1> | A missing public intermediate or an untrusted public chain belongs to the server certificate and deployment owner. A chain that ends at the enterprise inspection CA belongs to corporate network and endpoint-management owners: inspection requires clients to trust that CA, and the root must be installed in their trusted store. <https://learn.microsoft.com/en-us/entra/global-secure-access/how-to-transport-layer-security-settings-managed-certificate#download-and-deploy-the-root-ca-certificate> |
| Certificate differs only on the corporate network | Compare the client-visible issuer and chain on each path. TLS inspection terminates the client connection, opens a separate connection to the destination, then decrypts and re-encrypts traffic; the client sees an enterprise-CA-signed certificate. <https://learn.microsoft.com/en-us/entra/global-secure-access/tutorial-internet-access-tls-inspection#how-does-tls-inspection-work> | Corporate TLS inspection and endpoint trust-store owners. Do not change the public-origin certificate until the client-visible issuer rules out interception. <https://learn.microsoft.com/en-us/entra/global-secure-access/how-to-transport-layer-security-settings-managed-certificate#download-and-deploy-the-root-ca-certificate> |
| Public-origin certificate fails on a Caddy-hosted site | Inspect the public certificate that reaches the client directly, including its hostname, validity, and chain. Clients must validate the entire certification path as well as service identity. <https://www.rfc-editor.org/rfc/rfc9525.html#section-1.2> | Caddy and deployment owner. Caddy's automatic HTTPS provisions certificates for qualifying site addresses, renews them, and redirects HTTP to HTTPS. It does not identify or replace a certificate generated by a corporate inspection service. <https://caddyserver.com/docs/automatic-https> <https://learn.microsoft.com/en-us/entra/global-secure-access/tutorial-internet-access-tls-inspection#how-does-tls-inspection-work> |

## Short triage path

1. Capture the requested host, the certificate chain visible to the failing client, its issuer, `dNSName` entries, and validity dates. These are the inputs needed to separate identity, time, and path failures. <https://www.rfc-editor.org/rfc/rfc9525.html#section-6> <https://www.rfc-editor.org/rfc/rfc5280.html#section-6.1.1>
2. Compare that capture with the same host on a path where corporate inspection is not applied, when policy permits. An enterprise-signed client-visible certificate identifies the inspection path; the public-origin certificate identifies the server path. <https://learn.microsoft.com/en-us/entra/global-secure-access/tutorial-internet-access-tls-inspection#how-does-tls-inspection-work>
3. Route an enterprise-signed chain failure to corporate network and endpoint management. Confirm the inspection CA is active and its root is in the failing device's trusted store. <https://learn.microsoft.com/en-us/entra/global-secure-access/how-to-transport-layer-security-settings-managed-certificate#download-and-deploy-the-root-ca-certificate>
4. Route a public-origin chain failure to the server deployment owner. For Caddy, check the site address and automatic HTTPS certificate-management state, then correct the hostname, validity, or served chain that the client observed. <https://caddyserver.com/docs/automatic-https> <https://www.rfc-editor.org/rfc/rfc9525.html#section-1.2>
5. Close the incident only after the originally failing client validates the intended hostname and certification path on its normal production path. <https://www.rfc-editor.org/rfc/rfc9525.html#section-6.6> <https://www.rfc-editor.org/rfc/rfc5280.html#section-6>
